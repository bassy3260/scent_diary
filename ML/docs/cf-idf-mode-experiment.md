# CF 추천 IDF 가중치 개선 — User-IDF의 숨은 결함을 찾고 Catalog-IDF로 교체

작성일: 2026-09-06

---

## 요약

| 항목 | 내용 |
|---|---|
| **문제 상황** | 협업 필터링(CF) 추천의 IDF(희귀도 가중치)가 "소수 취향이 묻히지 않게 한다"는 원래 목적을 실제로 달성하고 있는지 검증되지 않은 채 서비스되고 있었음 |
| **방안 탐색** | 정량 평가 지표(Hit Rate@K, NDCG@K) 설계 → 실제 데이터 평가 → 합성 데이터로 알고리즘 sanity check → 두 가지 다른 시나리오(순수 취향군 구분 / 주력+소수 혼합 취향)로 IDF 방식 3종을 각각 8개 시드에 걸쳐 ablation |
| **기술 선정 이유** | "유저 기준 희귀도(User-IDF)"는 유저 표본이 작으면 실제 카탈로그 희귀도와 어긋나 왜곡됨을 실측으로 확인. "향수 카탈로그 기준 희귀도(Catalog-IDF)"는 고정된 전체 모집단(향수 1315건)을 기준으로 삼아 표본 편향에서 자유로움 |
| **성과** | 실제 서비스가 풀어야 하는 시나리오(주력 취향 속 소수 취향 보존)에서 Catalog-IDF **95.2%**, 기존 User-IDF **68.1%**, IDF 미사용 **65.3%** — 95% 신뢰구간이 전혀 겹치지 않는 통계적으로 확실한 차이 확인 후 실제 코드(`CfRecommender` 기본값)에 반영 |

## 포트폴리오/이력서용 요약 (바로 복붙용)

### 한 줄 (이력서 bullet)

> 협업 필터링 추천의 IDF 가중치 방식이 "소수 취향 보존"이라는 설계 의도를 실제로
> 달성하는지 leave-one-out 및 다수의 ablation 실험(8-seed, 95% 신뢰구간)으로 검증하고,
> 유저 표본 기반 계산 방식의 결함을 발견해 카탈로그 기반으로 교체 — 목표 지표를
> 65.3%→95.2%로 개선.

### 3~4문장 (프로젝트 설명란용)

> 협업 필터링(CF) 추천 모델의 정확도를 측정할 방법이 없어, leave-one-out 평가와
> baseline 비교(신뢰구간 포함) 지표를 직접 설계했다. 실제 데이터로는 표본이 작아
> 성능 검증이 어려워, 합성 데이터로 알고리즘을 단계적으로 ablation한 결과 핵심 구성
> 요소인 IDF 가중치가 "유저 표본" 기준이라 표본 편향에 취약하며, 실제로 원래 목적
> (주력 취향 속 소수 취향 보존)을 달성하지 못하고 있다는 걸 발견했다. 계산 기준을
> "향수 카탈로그 전체"로 바꿔 재검증한 결과, 목표 지표(희귀 취향 신호 생존율)가
> 65.3%에서 95.2%로 개선됐고(8개 시드, 95% 신뢰구간 완전히 비겹침) 실제 코드에 반영했다.

### STAR (면접 답변용)

- **S(상황)**: 협업 필터링 추천에 IDF 가중치가 적용돼 있었지만, 이게 실제로 의도한
  효과(소수 취향이 묻히지 않게 하는 것)를 내고 있는지 아무도 측정해본 적이 없었다.
- **T(과제)**: 정량적으로 측정할 방법을 만들고, 필요하면 근거를 갖고 개선한다.
- **A(행동)**: leave-one-out + baseline 비교 지표를 설계 → 실제 데이터로는 표본
  부족으로 판단 불가 확인 → 합성 데이터로 알고리즘 자체는 정상임을 sanity check →
  실제 IDF의 목적에 맞는 시나리오(주력+소수 혼합 취향)로 3가지 방식(유저 기준/카탈로그
  기준/미적용)을 8개 시드에 걸쳐 비교 → 유저 기준 방식이 표본 편향으로 원래 목적을 못
  살리는 걸 확인하고 카탈로그 기준으로 교체.
- **R(결과)**: 목표 지표 65.3% → 95.2%로 개선(신뢰구간 비겹침으로 통계적으로 확실),
  재사용 가능한 평가 스크립트 세트 확보, 실제 코드 반영 완료.

- `perfume` — 전체 향수 카탈로그, **1315건**(`is_delete=false`)
- `perfume_accord` + `accord` — 향수별 어코드 매핑. 카탈로그 전체 기준 개수 예시:

  1~5건짜리도 있음)
- `member_perfume` — 실제 소장 기록, **976건 / 유저 198명**. 1절(실제 데이터 1차 측정)
  에서만 사용했고, 그 이후 실험(합성 데이터)은 전부 향수-어코드 매핑만 실제 값을 쓰고
  "누가 뭘 소장했는가"는 인위적으로 만들었다.

때 정의가 살짝 갈렸다. 다만 두 실험 다 "레더가 top-K 추천에 살아남는가"만 측정하므로
최종 결론(9절)에는 영향이 없다.

### 샘플링 방법

- `random.Random(seed).sample(pool, N)`으로 매번 중복 없이 추첨. 풀이 유저 수보다 작은
  경우(예: 니치풀 22건인데 유저 60명)는 여러 유저가 같은 향수를 나눠 갖게 되는데,
  이건 실제로도 자연스러운 상황(향수 종류보다 소장자가 많은 경우)이라 그대로 둠.
- 섞인 프로필 실험(80명)은 시드마다 완전히 새로 추첨했고, **80명의 소장품 조합이
  실제로 80/80 전부 서로 다름을 직접 실행해서 확인**했다(같은 4+1 패턴이어도 구체적인
  향수는 유저마다 다름).
- 우연이 아님을 확인하기 위해 시드 8개(42, 1~7)로 반복.

## 1. 문제 상황

`CfRecommender`(협업 필터링 추천)는 BM25 TF × **User-based IDF**로 유저 취향 벡터를
만들고 있었다. IDF(Inverse Document Frequency)의 원래 존재 이유는 "누구나 다 가진
흔한 취향엔 낮은 가중치를, 소수만 가진 희귀한 취향엔 높은 가중치를 줘서, 주력 취향
속에 소수 취향이 묻히지 않게 하는 것"이다.

근데 이 코드는 **정말로 그 역할을 하고 있는지 한 번도 정량적으로 검증된 적이 없었다.**
"추천 정확도를 어떻게 측정할지"라는 질문에서 시작해 측정 파이프라인을 직접 만들었고,
그 파이프라인으로 검증하는 과정에서 IDF 계산 방식 자체에 결함이 있다는 걸 발견했다.

## 2. 방안 탐색

문제를 한 번에 풀지 않고, 가설을 세우고 → 검증하고 → 틀렸으면 다음 가설로 넘어가는
순서로 진행했다. 아래는 그 탐색 과정이다(상세 수치와 실험 스크립트는 4~9절 참고).

1. **측정 방법 설계**: leave-one-out(소장 향수 하나를 숨기고 나머지로 추천해서 그
   숨긴 걸 맞히는지 확인) + Hit Rate@K/NDCG@K + 인기순/무작위 baseline과 비교.
2. **실제 데이터로 1차 측정**: baseline들과 통계적으로 구분이 안 됨 → "알고리즘이
   나쁜 건지, 데이터가 부족한 건지" 판단이 필요해짐.
3. **합성 데이터로 알고리즘 자체를 sanity check**: 뚜렷한 인위적 패턴(우디파 vs
   플로럴파)을 만들어서 CF가 그 정도는 찾아내는지 확인 → 찾아냄. 즉 알고리즘 자체는
   정상, 1차 결과는 데이터 부족 때문이라는 근거 확보.
4. **희귀 어코드로 정밀 검증**: "레더"(카탈로그 전체 50건, 진짜 희귀) 취향군을 만들어
   재검증 → 오히려 IDF를 끄는 쪽이 계속 더 나음. 이 과정에서 **테스트 스크립트 자체의
   버그**(노이즈 로직이 모든 유저에게 강제로 희귀 어코드를 섞어버려 "희귀함" 자체를
   훼손)를 발견해 수정.
5. **"IDF 끄면 흔한 취향이 추천을 도배하지 않냐"는 반론 검증**: 실제로 확인해보니
   도배 현상 없음 — 기우로 판명.
6. **결정적 전환**: "순수하게 한 취향만 가진 유저" 구분은 애초에 IDF가 풀어야 할
   문제가 아니었다는 지적을 받아들여, **IDF가 정말로 존재하는 이유(주력 취향 속 소수
   취향 보존)에 맞는 시나리오**로 다시 설계 → User-IDF/Catalog-IDF/IDF 없음 3자
   비교로 8개 시드에 걸쳐 재검증.

## 3. 기술 선정 이유 — User-IDF에서 Catalog-IDF로

**기존 (User-IDF)**:
```
user_idf(어코드) = log(전체 유저 수 / 이 어코드를 가진 향수를 소장한 유저 수) + 1
```
희귀도의 기준이 "유저 집단"이다. 문제는 유저 표본이 작거나 특정 그룹에 편향되면,
실제로는 카탈로그 전체에서 흔한 어코드가 그 표본 안에서는 우연히 드물게 나타나
"가짜로 희귀"하다고 계산될 수 있다는 것 — 실측으로 확인됨(4절 상세 참고: 실제 카탈로그
기준으로 훨씬 흔한 "웜 스파이시"가, 작은 유저 표본에서는 진짜 희귀 신호인 "레더"보다
더 큰 가중치를 받는 역전 현상 확인).

**변경 (Catalog-IDF)**:
```
catalog_idf(어코드) = log(전체 향수 수 / 이 어코드를 가진 향수 수) + 1
```
희귀도의 기준을 "향수 카탈로그 전체"(고정된, 표본 편향이 없는 완전한 모집단)로 바꿨다.
추가 DB 조회 없이 이미 갖고 있는 `perfume_accord_map` 데이터로 바로 계산 가능해서
구현 비용도 거의 없다.

**최종 검증(6절 시나리오, IDF 실제 사용 목적에 맞는 테스트)에서 Catalog-IDF가 압도적
우위**를 보여, 이 방식으로 교체하는 근거가 통계적으로 확실해졌다.

## 4. 성과

### 4-1. 핵심 지표 (섞인 취향 프로필에서의 소수 신호 생존율, 8개 시드 종합)

유저 80명에게 "흔한 취향(우디) 향수 4개 + 희귀 취향(레더) 향수 1개"를 소장시키고,
추천 top-10에 레더 향수가 하나라도 살아남는 유저의 비율:

| 방식 | 생존율 | 95% 신뢰구간 |
|---|---|---|
| **Catalog-IDF (변경 후)** | **95.16%** | [0.9321, 0.9657] |
| User-IDF (변경 전) | 68.12% | [0.6442, 0.7162] |
| IDF 미사용 | 65.31% | [0.6154, 0.6890] |

신뢰구간이 전혀 겹치지 않아 통계적으로 확실한 차이다. 특히 **기존 User-IDF(68.1%)는
IDF를 아예 안 쓴 것(65.3%)과 사실상 차이가 없어**, 기존 코드의 IDF가 존재 이유(소수
취향 보존)를 사실상 못 하고 있었다는 것도 함께 확인됐다.

### 4-2. 코드 반영

```python
# app/services/cf_recommender.py
class CfRecommender:
    def __init__(self, bm25_k: float = BM25_K, idf_mode: str = "catalog"):  # "user" -> "catalog"
```

### 4-3. 부수적으로 얻은 것

- CF 추천 알고리즘 자체의 정합성을 검증하는 재사용 가능한 평가 스크립트 5종 확보
  (`scripts/evaluate_cf*.py`, `scripts/debug_*.py`) — 앞으로 알고리즘을 더 손볼 때
  "전/후 비교"할 수 있는 기준선이 생김.
- 테스트 스크립트 자체의 버그(강제 노이즈 주입 로직)를 발견/수정 — 실험 방법론 자체의
  신뢰도를 한 단계 검증.
- "IDF를 끄면 흔한 취향이 추천을 도배한다"는 가설을 실제로 반증 — 근거 없는 우려와
  근거 있는 결함을 구분.

## 5. 상세: 실제 데이터 1차 측정

```
CF (user-IDF)      Hit Rate@10: 0.0083 [0.0042, 0.0163] (8/962건)
인기 향수 baseline  Hit Rate@10: 0.0052 [0.0022, 0.0121] (5/962건)
무작위 baseline     Hit Rate@10: 0.0104 [0.0057, 0.0190] (10/962건)
```

세 방법의 95% 신뢰구간이 전부 겹친다. 원인은 데이터 희소성(소장 기록 976건 / 유저 198명
/ 향수 1315건, 밀도 약 0.37%)으로 판단 — leave-one-out 자체가 "유저당 평균 5개도 안 되는
소장품 중 하나를 1300여 개 후보 중에서 정확히 맞히는" 원래 어려운 과제라, 이 정도
데이터양에선 알고리즘 우열이 통계적으로 드러나지 않는다.

**스크립트**: `scripts/evaluate_cf.py`

## 6. 상세: 알고리즘 자체는 정상 동작함 (합성 데이터 sanity check)

"진짜 정확도"와 별개로, "알고리즘이 뚜렷한 패턴이라도 제대로 찾아내는가"를 확인하기
위해 실제 카탈로그(어코드 매핑)는 그대로 두고 소장 데이터만 인위적으로 만들어 테스트.
그룹 A는 "우디" 계열만, 그룹 B는 "플로럴" 계열만 소장하게 하고 leave-one-out 평가:

```
Hit Rate@10: 0.0423 (무작위 기대값 0.0076 대비 5배 이상, 신뢰구간 전혀 안 겹침)
어코드 겹침률(추천 top-10에 숨긴 향수와 같은 계열이 하나라도 있는가): 98.97%
```

→ **CF는 "이 유저가 어느 취향 클러스터에 속하는지"는 거의 완벽하게 잡아낸다.** 5절의
낮은 성능은 알고리즘 버그가 아니라 데이터 부족 때문이라는 근거.

**스크립트**: `scripts/evaluate_cf_synthetic.py`

## 7. 상세: "순수 클러스터 구분"에서는 IDF가 오히려 방해됨 (테스트 버그 발견 포함)

희귀 어코드("레더", 카탈로그 전체 50개)로도 클러스터를 잘 구분하는지 확인하려고
"우디+레더"(니치, 22개) vs "우디만"(일반, 443개) 그룹으로 재실험. 처음엔 IDF를 그냥
꺼봤을 때가 켰을 때보다 일관되게 나은 결과가 나왔다(8개 시드 전부).

**중간에 발견한 진짜 버그**: 노이즈를 섞는 코드가 `max(1, round(n_owned*ratio))`로 되어
있어서 **모든 유저에게 무조건 최소 1개씩 다른 그룹 향수가 섞이게** 되어 있었다. 그 결과
"레더"가 인위적으로 전체 유저 절반 이상이 갖게 되어, IDF 계산 자체가 "레더는 안
희귀하네"로 왜곡됐었다. CF의 버그가 아니라 **테스트 스크립트의 버그**였다 —
`rng.random() < NOISE_RATIO`로 개별 확률 판정하도록 고침.

버그를 고친 뒤 재실행해도 경향은 그대로 유지됨(8/8 시드에서 IDF 없음이 우세, 격차만
줄어듦). 벡터를 직접 찍어서 원인을 봤더니:

```
[니치 유저 벡터, 0 아닌 성분]
  웜 스파이시 : 0.5713   ← 레더보다 큼!
  우디        : 0.5509
  레더        : 0.5198   ← 원래 핵심 신호인데 상대적으로 밀림
```

**원인**: 니치 향수 22개 중 "웜 스파이시"를 가진 건 4개뿐이라, 유저 기준 IDF로 보면
웜 스파이시가 레더보다 더 "희귀"하게 계산됨 — 근데 웜 스파이시는 그룹을 가르는 진짜
신호가 아니라 몇몇 향수에 우연히 붙은 부수적 특성이었다. "통계적 희귀함"과 "판별력"은
다른 개념인데 IDF가 그 둘을 같다고 가정한다는 게 근본 원인.

카탈로그 기준(`idf_mode="catalog"`)도 추가해서 3자 비교를 했는데, **이 시나리오에서는
셋 다** IDF 없는 쪽보다 나빴다. 이 시점 결론은 "IDF를 그냥 끄자"였다 — **결과적으로
틀린 결론이었다** (8절 참고).

**스크립트**: `scripts/evaluate_cf_rare_signal.py`, 디버깅용 `scripts/debug_idf.py`

## 8. 상세: "홍수" 우려 검증

"IDF를 끄면 우디처럼 흔한 어코드가 추천을 뒤덮지 않냐"는 지적으로 직접 검증. 120명
전체의 top-10 추천에 등장한 서로 다른 향수 개수를 IDF 켰을 때/껐을 때 비교:

```
IDF 켰을 때: 220건 서로 다른 향수 등장, 최다 추천 향수 45.0%
IDF 껐을 때: 196건 서로 다른 향수 등장, 최다 추천 향수 45.8%
```

거의 차이 없음 — "홍수"는 기우였다. 이유: 우디는 니치/일반 두 그룹 "모두"에게 공통인
배경 신호라, 그 가중치를 만져도 후보 간 상대 순위(누가 더 위냐)는 별로 안 바뀐다.

**스크립트**: `scripts/debug_flooding.py`

## 9. 상세: 결정적 발견 — "섞인 프로필"에서는 Catalog-IDF가 압승

7절까지의 테스트가 전부 잘못된 질문을 던지고 있었다는 지적을 받고 방향을 바꿨다.
"순수하게 한쪽만 소장한 유저" 클러스터 구분은 애초에 IDF가 풀어야 할 문제가 아니다
(8절에서 이미 확인). **IDF가 정말로 존재하는 이유는 "주력 취향 안에 소수 취향이
묻히지 않게 하는 것"** — 훨씬 현실적인 시나리오(대부분 유저는 순수 한 계열이 아니라
"주로 A, 가끔 B" 식)다.

**테스트**: 유저 80명, 각자 "우디 향수 4개 + 레더 향수 1개"를 소장. 추천 top-10에
레더 향수가 하나라도 살아남는지(생존율)를 8개 시드로 측정한 결과가 위 4-1절의 표.
**catalog-IDF가 압도적으로 우수**했고, 이게 최종 결정 근거가 됐다.

**스크립트**: `scripts/evaluate_cf_minority_signal.py`, 단일 사례 확인용
`scripts/debug_mixed_profile.py`

## 한계 및 후속 과제

- 실제 데이터(5절)에서는 표본이 작아 CF 전체의 우열 자체가 아직 통계적으로 증명 안 됨.
  이번 catalog-IDF 교체가 실제 서비스 지표(클릭률, 소장 전환 등)에 미치는 영향은 별도로
  관찰 필요.
- 이번 실험은 전부 "우디+레더" 한 조합만으로 확인함. 다른 어코드 조합, 다른 희석 비율
  (예: 8:1, 2:1)에서도 같은 경향인지는 확인 안 함.
- `_rank_normalize`, `_dynamic_alpha` 등 CF의 다른 구성요소는 이번에 손 안 댐.
- 실제 프로덕션 데이터(합성이 아닌 실제 976건)로 이 "섞인 프로필 생존율" 지표를 재보는
  것도 후속 실험 후보(단, 실제 유저 중 "주력+소수" 패턴이 뚜렷한 사람이 몇 명이나
  있는지부터 확인 필요).
